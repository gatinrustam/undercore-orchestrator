# Диагностика и метрики

Диагностика включается при стандартном запуске через bootstrap: JSON-события пишутся
в stderr и попадают в journald, метрики доступны через служебный HTTP API.
Внешний Prometheus или Grafana не требуются для работы VPN. Их установка и панели
визуализации не входят в этот этап.

## Корреляция запросов

Каждый входящий HTTP-запрос получает новый `X-Request-ID` (32 шестнадцатеричных
символа), включая ошибки авторизации и валидации. Переданный вызывающей стороной
идентификатор не принимается: в нём могут оказаться секреты или чужая корреляция.
Backend может сохранить возвращённый заголовок рядом со своим идентификатором.
Тело ответа и коды ошибок v1/v2 сохраняют прежний контракт.

Тот же идентификатор передаётся агентам в X-Request-ID. Для операции также передаётся
X-Operation-Ref. Старый агент может игнорировать эти заголовки; чтение и сохранение
корреляции на стороне самого агента потребует отдельной реализации. Контекст
переносится в потоки параллельной проверки узлов и не смешивается между запросами.

Повтор запроса получает новый request_id. `operation_ref` позволяет связать попытки
одной операции: для переключения он вычисляется из connection_id и сохранённого
operation_id. Фоновое продолжение сохраняет эту ссылку. Она предназначена только
для диагностики и не заменяет ключ идемпотентности или авторизацию.

`operation_ref` и `node_ref` — первые 24 hex-символа SHA-256 от строк с 8-байтовыми
префиксами длины; функция `application.telemetry.reference` задаёт точный формат.
Для node_ref используется node_id. Это псевдонимы, а не гарантия анонимности:
известный идентификатор можно сопоставить с его хешем. Они не являются метками метрик.

## События

```sh
journalctl -u vpn-orchestrator.service -u vpn-orchestrator-recovery.service -u vpn-orchestrator-leases.service --since '1 hour ago' -o cat
```

Завершение этапа записывается как JSON с фиксированными полями: timestamp, event,
stage, action, reason, duration_ms, request_id и, если применимо, operation_ref,
node_ref, http_status. Временные интервалы измеряются монотонными часами.

Этапы включают HTTP-запрос, создание, выбор/проверку узла, запрос агента, получение
параметров, экспорт, переключение, recovery, фоновую сверку и heartbeat.
У запросов агента action различает health, list, create, connection и мутации.
Вложенные этапы пересекаются: складывать их длительности или считать их количество
числом пользователей нельзя. Событие завершения появляется после возврата или ошибки;
отдельных событий начала и длительных распределённых traces пока нет.

| reason | Интерпретация |
|---|---|
| ok | Этот этап завершился без ошибки; не подтверждает интернет у пользователя |
| deadline | Исчерпан общий бюджет прикладной операции |
| saturated | Переполнена локальная очередь или истекло ожидание допуска |
| timeout | HTTP-клиент достиг своего таймаута |
| tls | В цепочке транспортной ошибки обнаружена SSL-ошибка |
| network | Другая транспортная ошибка; не доказательство блокировки |
| upstream_status | Агент вернул неуспешный HTTP-статус |
| invalid_response | Не удалось декодировать/проверить ответ или нарушен лимит/требование no-store |
| identity_mismatch | Ответ не соответствует ожидаемому узлу/назначению |
| waiting | Незавершённая операция, блокировка или ожидание lease |
| unavailable / rejected | Сервисная ошибка доступности или отклонённая операция |
| unauthorized / validation | Отказ авторизации или проверка входных данных HTTP |
| internal_error / cancelled | Неожиданный сбой или отмена операции |

Если библиотека не сохраняет исходную SSL-ошибку, TLS-сбой может попасть в network.
Произвольный текст исключений не анализируется и не записывается. Внешний статус
node_unavailable остаётся прежним; подробная категория доступна в диагностике.

В событиях нет URL, query string, IP-адресов, имён устройств, входных/выходных тел,
токенов и VPN-документов. Ошибка при записи события не отменяет VPN-операцию.
Логи синхронные: медленный stderr может добавить задержку, поэтому состояние
системного журнала также требует контроля. Retention задаётся оператором в journald;
дополнительно bootstrap сохраняет безопасные события в ограниченный EventTail для
[панели](panel.md): два файла по 256 КиБ, до 100 последних событий в ответе.
Межпроцессная блокировка не ожидается: при конкуренции или ошибке событие может
пропасть. Это диагностическая выборка, не надёжный аудит. Запись на медленный диск
может добавить задержку; ошибки записи не отменяют операцию.

## Метрики

`GET /internal/v1/metrics` использует существующий backend Bearer-токен и no-store.
Сервис по умолчанию слушает loopback. Не публикуйте endpoint через открытый reverse
proxy; токен даёт полномочия backend, а не только чтение метрик. Отдельная панель имеет только API обзора; она не открывает этот endpoint метрик
своим ключом. Не размещайте токен в
командной строке, истории shell или открытом конфиге сборщика.

Используется стандартный prometheus-client. Собственная registry не включает
сторонние/default process collectors. Метки stage, action и reason ограничены
перечислениями; идентификаторов, произвольных путей и пользовательских значений нет.

| Метрика | Назначение |
|---|---|
| orchestrator_operations_total | Количество завершённых этапов по stage/action/reason |
| orchestrator_operation_duration_seconds | Гистограмма длительности по stage/action |
| orchestrator_pending_operations{kind="create"} | Назначения без подтверждённого remote_id |
| orchestrator_pending_operations{kind="switch"} | Незавершённые переключения |
| orchestrator_oldest_pending_seconds | Возраст самого старого незавершённого переключения |
| orchestrator_journal_snapshot_success | Успешность последнего чтения локального журнала |

Просмотр метрик не обращается к VPN-агентам. Очередь читается из SQLite в режиме
read-only без резервирования записи, с коротким ожиданием блокировки. Если БД
недоступна, snapshot_success равен 0, прежние значения очереди могут быть устаревшими.
Пустая очередь не означает, что у всех пользователей исправно работает VPN.

Счётчики и гистограммы относятся к текущему процессу API и сбрасываются при его
перезапуске. Короткоживущие workers пишут события в journald; их счётчики не
суммируются в API-процессе. Состояние очереди читается из общего постоянного журнала.
Экземпляры API имеют отдельные registry: при нескольких процессах их нужно собирать
раздельно. Этот выпуск не добавляет multiprocess Prometheus storage.

Пример p95 времени выбора узла при наличии Prometheus:

```text
histogram_quantile(0.95,
  sum by (le) (rate(orchestrator_operation_duration_seconds_bucket{stage="select_node",action="none"}[5m]))
)
```

Для расследования задержки найдите HTTP-событие по request_id, затем этапы выбора
узла, обращения к агенту и получения конфигурации. Для повторяющегося переключения
сопоставьте operation_ref в API и worker-журнале. Проверяйте конкретную причину:
сбой управляющего API не подтверждает сбой пользовательского туннеля.

Этап `agent_queue` измеряет ожидание допуска к общему и узловому лимиту.
[Границы нагрузки и сроков](runtime-limits.md) применяются независимо от сбора метрик.
