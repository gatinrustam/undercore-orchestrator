# Сообщение об уязвимости

Не публикуйте ключи, токены, конфигурации туннеля или данные пользователей в Issues,
Pull Requests и примерах воспроизведения.

Если на странице GitHub Security этого репозитория доступна кнопка **Report a
vulnerability**, используйте её. Включение private vulnerability reporting ещё
нужно проверить перед публичным выпуском; наличие этого документа не включает
функцию GitHub. Если кнопки нет, создайте Issue только с просьбой предоставить
приватный канал, без описания эксплуатации и чувствительных данных.

Для приватного сообщения подготовьте версию/commit, затронутый компонент,
ожидаемое и фактическое поведение, минимальный пример с синтетическими данными.
У проекта пока нет обещанного SLA обработки и политики поддержки старых веток.

## Границы доверия

API вызывается доверенным backend по служебному Bearer-токену. Backend проверяет
пользователя и право на действие. Это не многоарендная граница между недоверенными
backend: токен даёт полномочия управления техническими назначениями.

У каждого узла отдельный токен и проверяемая server identity. HTTP-ответы с
конфигурациями секретны. SSH для установки узла не должен превращаться в runtime
зависимость выдачи подключения. Вопросы безопасной эксплуатации описаны в
[операциях](operations.md) и [контракте агента](node-agent.md).


## Классификация данных

| Данные | Допустимое использование |
|---|---|
| Backend-токен и токены агентов | Приватные файлы, память процесса, защищённый Authorization-заголовок; не Git, URL, журналы или ответы API |
| Приватные VPN-ключи, документы конфигурации, содержимое QR | Память при выдаче авторизованному получателю; не центральная SQLite, диагностика или логи |
| Идентификаторы устройства, подключения и операции | Журнал технического состояния; ограниченный операторский доступ, без публичных списков |
| IP/адреса API узлов, состояние, сроки доступа | Настройки и техническое состояние; не общедоступная диагностика |
| Пароли пользователя, оплата и свободные слоты | Система заказчика; оркестратору не передаются |

Ответы с параметрами имеют no-store. Это не предотвращает запись внешним reverse
proxy: его конфигурация также должна исключать тела и Authorization. Новые логи
формируются по разрешённому набору полей; произвольный текст upstream-ошибки или
repr объекта нельзя включать в событие. Структурированные события и метрики описаны в [диагностике](observability.md).
Их проверки покрывают секреты в исключениях, заголовках, URL и выдаваемых документах.

## Управление и панель просмотра

Изменения выполняет локальный CLI или панель с явно включённым `--manage`,
с правами сервисного пользователя. Backend доверен
для технических назначений, но не управляет серверным реестром через HTTP.
[Панель](panel.md) работает отдельно на loopback, со своим ключом: совпадение с
backend-ключом блокирует запуск. Прежний `admin_token_file` не используется.

Сессия хранится в памяти процесса один час; cookie HttpOnly/SameSite=Strict.
Проверяются Host, Origin для POST и Sec-Fetch-Site. Ответы запрещают кэширование,
встраивание во фреймы и внешние ресурсы через CSP. Ключи не сохраняются в браузерном
хранилище. Удалённый доступ — через SSH forwarding, без публикации порта.
В режиме просмотра нет мутаций. Режим управления принимает URL и ключ агента
только на входе; они не попадают в аудит и ответы. VPN-документы не выдаются. Это административные
данные, поэтому их нельзя считать публичными. Ключ панели с `--manage` имеет полномочия оператора. Персональных ролей пока нет;
метка cli/panel в аудите показывает канал команды, а не личность пользователя.
[Проверки выпуска](release-security.md) включают автономный поиск секретов
и проверку зависимостей по публичной базе уязвимостей.
