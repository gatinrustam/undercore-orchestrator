# Нагрузка и сроки выполнения

Оркестратор переиспользует HTTP-соединения с агентами. На процесс создаётся один
HTTPX AsyncClient и отдельный цикл asyncio; синхронный драйвер ждёт результат.
Работа с SQLite и блокировки назначений остаются в вызывающем потоке.
Это позволяет прерывать сетевое ожидание по общему сроку, включая ответ, который
приходит маленькими частями, без оставленного фонового потока мутации.
Используются [жизненный цикл HTTPX](https://www.python-httpx.org/async/) и
[отмена по сроку asyncio](https://docs.python.org/3.12/library/asyncio-task.html#asyncio.timeout).

## Настройки

Поля находятся в `policy.agents` файла settings.json; [границы значений](configuration.md).

```json
{
  "policy": {
    "agents": {
      "operation_timeout_seconds": 30,
      "queue_timeout_seconds": 2,
      "max_concurrent_requests": 16,
      "max_concurrent_per_node": 4,
      "max_pending_requests": 64,
      "max_pending_per_node": 8,
      "connect_timeout_seconds": 4,
      "response_timeout_seconds": 12
    }
  }
}
```

- До 16 исходящих HTTP-запросов одновременно, до 4 на один узел.
- До 64 принятых обращений к транспорту, включая выполняющиеся и ожидающие.
  До 8 обращений на узел: один занятый сервер не может заполнить всю очередь.
  При заполнении любого pending-лимита новое обращение отклоняется сразу.
- Ожидание допуска — до 2 секунд. Сначала берётся место узла, затем общее:
  очередь занятого узла не резервирует глобальные места.
- Один HTTP-запрос ограничен 12 секундами целиком, а установление соединения — 4.
  Ранее response_timeout ограничивал отдельное ожидание чтения; теперь медленная
  непрерывная передача тоже ограничена. Пределы размеров ответа сохранены.
- Прикладная операция имеет общий бюджет 30 секунд. Проверка идентичности,
  наблюдения серверов, чтение параметров и мутации используют остаток этого
  бюджета. Вложенный вызов не начинает отсчёт заново.

Лимиты относятся к одному экземпляру runtime. API, recovery и lease-worker имеют
собственные пулы; пользовательская очередь API не занимает места heartbeat.
Это не общая квота между процессами или машинами. Перезапуск применяет настройки;
увеличение числа процессов умножает суммарную нагрузку на агенты.
`selection.observation_workers` по-прежнему ограничивает параллельный обход в одном
запросе; исходящие обращения всех обходов дополнительно проходят общий ограничитель.

## Что ограничивает общий срок

Отсчёт начинается при входе в прикладной сценарий. Он не включает загрузку тела
входящего HTTP-запроса или ожидание потока FastAPI. Ожидания HTTP и допуска отменяются
по сроку; межпроцессная блокировка и ожидание SQLite используют остаток времени.
Новая выдача после истечения бюджета не запускается. В recovery бюджет задаётся
на одно назначение, в heartbeat — на один узел, а не на весь проход.

Бюджет не является жёстким пределом доставки HTTP-ответа: фиксация уже полученного
результата, rollback/закрытие ресурсов, работа диска и синхронная запись логов не
прерываются насильно. После подтверждённой мутации нужно сохранить её результат,
даже если сеть заняла весь отведённый срок. Ограничения reverse proxy и systemd
должны учитывать это завершение, а не убивать процесс ровно на 30-й секунде.

## Повторы и отказ узла

Автоматических транспортных повторов нет, включая POST. Отмена запроса на нашей
стороне не отменяет действие у агента. Назначение и ключ сохраняются до отправки;
повтор создаёт/находит тот же peer на закреплённом узле. Незавершённое переключение
продолжает журналируемую операцию с подтверждённым отзывом старого доступа.

Переполненная локальная очередь возвращает прежний `503 connection_busy`, общий
срок — `503 node_unavailable`. Внутри сервиса это отдельные типы ошибок: recovery
и switch не принимают их за отказ исходного сервера и не закрывают его разрешение.
Доверенный backend повторяет исходный запрос с задержкой и ограничением попыток;
новый device_id или новый ключ для обхода ошибки использовать нельзя.

Диагностика добавляет `agent_queue` для времени допуска и причины `saturated` и
`deadline`. Эти данные помогают отличить перегрузку оркестратора от ответа агента.
Ни один из этих сигналов сам по себе не доказывает сбой пользовательского туннеля.

## Жизненный цикл и проверки

HTTP-пул закрывается при завершении API, CLI и worker. Ключ передаётся только
заголовком конкретного запроса; cookies агентов не сохраняются. Проверки TLS,
server identity, запрет перенаправлений и игнорирование proxy-переменных сохранены.
Пул не содержит кэша конфигураций и не записывает секретные ответы на диск.

`tests/test_runtime_limits.py` проверяет общую и узловую параллельность, переполнение,
отмену очереди и медленного потока, восстановление после потери ответа создания,
отсутствие ложного переноса и закрытие runtime. Тест с временным HTTP-сервером на
loopback проверяет настоящее переиспользование TCP и изоляцию заголовков; для него
нужны разрешённые локальные сокеты. Конфигурация рабочих узлов по-прежнему требует HTTPS.
