# Гарантии жизненного цикла

Это контракт текущего поведения и обязательные условия будущего рефакторинга.
Реализация проверяется тестами с закреплённым агентом, без реальных VPN-серверов.
Общий набор испытаний драйверов находится в tests/test_driver_contract.py.

## Идентификаторы

| Значение | Владелец и срок жизни |
|---|---|
| `device_id` | Канонический идентификатор устройства/доступа от доверенного backend; право на слот проверяет backend |
| `connection_id` | Стабильный идентификатор подключения оркестратора; сохраняется при переносе между узлами |
| `node_id` / `server_id` | Запись узла и ожидаемая идентичность агента; подмена адреса не разрешает принять чужой сервер |
| `remote_id` | Идентификатор peer на конкретном узле; может измениться при переносе |
| `binding_key` | Идентичность создания peer; повтор после потери ответа использует прежнее значение |
| `idempotency_key` | Идентичность конкретной операции; таймаут не разрешает заменить ключ |
| `revision` | Ревизия полученных параметров; повтор старой ревизии не должен переключать устройство обратно |

Уникальность журнала назначений задана для пары `(device_id, protocol)`.
Это техническое ограничение, а не учёт оплаченных слотов. Текущий сценарий create
сначала использует совместимое существующее назначение; несовместимый запрос не
разрешает молча создать второй доступ. Межпротокольная миграция пока не реализована.

## Состояние доступа и состояние сети

В модели Connection допустимы `pending`, `active`, `disabled`, `expired`, `conflict`.
HTTP-слой описывает проверенный ответ агента; не каждое промежуточное состояние
возвращается клиенту как Connection — операция может завершиться машинной ошибкой.

`active` означает разрешённый доступ на узле. Это не свидетельство свежего handshake,
работающего DNS или доступности сайта с устройства пользователя. Оркестратор видит
свою связь с API агента; клиент наблюдает собственную сеть и туннель. Таймаут API,
ошибка сайта и недоступность туннеля не взаимозаменяемы. Проверка `/v1/health`
подтверждает работу процесса, а не исправность всех VPN-узлов.

## Первое создание

1. Backend проверяет владельца, подтверждение аккаунта, срок и доступный слот.
2. Оркестратор проверяет входной контракт и совместимость клиента/драйвера.
3. Для нового назначения получает свежие наблюдения и резервирует место в SQLite.
   При подсчёте учитывает конкурентные назначения и незавершённые переключения.
4. Создаёт peer на закреплённом узле с сохранённой идентичностью.
5. Проверяет ответ и возвращает стабильный connection_id.

Потеря ответа между шагами 4 и 5 оставляет неопределённый результат, а не доказательство
отсутствия peer. Повтор восстанавливает то же назначение на том же узле. Новая цель
или новый binding_key в обход журнала недопустимы.

## Переключение узла

Переключение сегодня сохраняет протокол. В таблице switches сохраняются состояния:

| Состояние | Значение и допустимое продолжение |
|---|---|
| `reserved` | Цель, ключ операции и binding_key сохранены; подтвердить прекращение старого доступа |
| `source_revoked` | Прекращение доступа подтверждено; создать/найти peer на закреплённой цели и проверить его |
| `complete` | Назначение и результат переключения опубликованы одной транзакцией |
| `cancelled` | Просроченная операция закрыта после проверки отзыва; новый доступ не создаётся |

При таймауте состояние остаётся на последнем подтверждённом шаге. Повтор может снова
вызвать агент, поэтому его операции должны быть идемпотентными. Фоновый обработчик
продолжает ту же операцию после перезапуска; третий сервер не выбирается.

Новый доступ выдаётся после подтверждённого отзыва источника. Исключение для полного
отказа API допускается только при проверенном механизме коротких разрешений (leases)
и завершённом безопасном ожидании. Обычный таймаут не заменяет отзыв. На узлах без
leases автоматическое завершение переноса при недоступном источнике невозможно.
Подробнее: [контракт агента](node-agent.md).

Запрос disable во время переключения сохраняет `disable_requested` до продолжения
операции. Восстановление не должно опубликовать активный доступ после этого запроса.
Истёкший срок не продлевается автоматически. Просроченная операция отменяется после
проверки отзыва обеих сторон. Старый завершённый запрос не заменяет новое назначение.

## Выдача параметров и экспорт

Перед выдачей проверяются принадлежность устройству, совместимость, идентичность
узла, срок, запрет доступа и незавершённые операции. Изменение назначения и выдача
параметров используют общую блокировку. Экспорт не создаёт peer, не продлевает срок
и не переключает сервер; после обращения к агенту срок проверяется повторно.

Формат выбирается из возможностей адаптера. Неизвестный формат или несовместимый
клиент получают явную ошибку, без скрытой подмены протокола. Конфигурационные
документы проходят через память и не сохраняются в центральном журнале.

## Карта регрессионных проверок

Исходники тестов находятся в [tests](https://github.com/UndercoreCo/orchestrator/tree/main/tests).

| Гарантия | Существующая проверка |
|---|---|
| Повтор и конкурентное создание не дают второго peer | `test_agent_gateway.py`: `test_concurrent_creates_consume_one_assignment` |
| Потеря ответа сохраняет узел и идентичность | `test_agent_gateway.py`: `test_lost_response_recovers_original_node_peer_and_assignment` |
| Неверный server_id блокирует команды | `test_agent_gateway.py`: `test_server_identity_mismatch_blocks_commands_even_for_existing_assignment` |
| Чужое устройство не получает и не отзывает доступ | `test_connection_contract.py`: `test_wrong_device_cannot_read_export_or_revoke` |
| Неподтверждённый отзыв блокирует выдачу на цели | `test_node_switch.py`: `test_revoke_unreachable_never_creates_target_and_can_resume` |
| Перезапуск продолжает прежнее переключение | `test_node_switch.py`: `test_lost_response_recovers_same_switch_after_restart` |
| Намерение отключить сохраняется при отказе цели | `test_node_switch.py`: `test_disable_intent_survives_target_outage_and_switch_retry` |
| Перезагрузка и скачок часов не сокращают безопасное ожидание | `test_leases.py`: `test_wall_clock_jump_and_host_restart_cannot_shorten_fence` |
| Старая revision не вызывает обратное переключение | `test_recovery.py`: `test_stale_revision_returns_new_manifest_without_switch` |
| Экспорт не создаёт назначения | `test_exports.py`: `test_exports_are_adapter_owned_and_do_not_create_assignments` |
| Неудачное обновление сохраняет актуальный журнал | `test_standalone.py`: `test_failed_health_rolls_back_code_without_restoring_live_journal` |

Эти проверки подтверждают конкретные сценарии. Они не заменяют испытания реального
VPN-движка, сети клиента, нагрузки и установки на чистом сервере.
